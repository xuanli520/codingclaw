# Artifact Layout Specification

## Purpose

This document defines the required archive structure for every CodingClaw job.

## Job Root Layout

Each job archive must include:

```text
jobs/<job_id>/
  repo/
  state/
  approvals/
    <card_id>/
      approval-card.json
      decision.json
      summary.zh.md
  artifacts/
    runs/
      <run_id>/
        reports/
          handoff.en.md
          implementation-summary.en.md
          self-check.en.md
          qa-report.en.md
          review-report.en.md
          fixback-items.en.md
        logs/
          command-log.txt
          worker.log
        evidence/
          test-results/
          screenshots/
          ci-exports/
        metadata/
          task-packet.en.json
          run-result.json
          artifact-index.json
          qa-verdict.json
          timings.json
        takeover/
          takeover-packet.en.md
          result.en.md
    sessions/
      builder/
      qa/
    final/
      final-summary.en.md
    metadata/
      environment.json
  runtime-home/
  DEVELOPMENT_PLAN.en.md
  CONTRACT_FREEZE.en.md
  contract-freeze.json
  contract-freeze.sha256
  job-manifest.json
  checksums.txt
```

## Run-Scoped Layout

Each execution loop must allocate one unique `run_id`.

All loop-specific outputs live under `artifacts/runs/<run_id>/`.

Canonical filenames remain stable inside that run root, including:

- `logs/command-log.txt`
- `metadata/task-packet.en.json`
- `metadata/run-result.json`
- `metadata/artifact-index.json`
- `reports/handoff.en.md`

Role-specific reports are optional by run type, but when produced they must stay inside the same `run_id` root.

## Approval Archive

Approval objects are long-lived control-plane evidence and must not be mixed into per-run worker output trees.

- `approvals/<card_id>/approval-card.json` stores the card payload
- `approvals/<card_id>/decision.json` stores the decision receipt
- `approvals/<card_id>/summary.zh.md` stores the Chinese owner-facing summary when it exists
- `job-manifest.json` must reference these approval artifacts

## Required Rules

- every path written by a worker must be declared in the artifact index
- every loop-specific path must stay under `artifacts/runs/<run_id>/`
- `contract-freeze.sha256` must live beside the freeze objects at the job root
- `logs/command-log.txt` is the canonical per-run command transcript name
- `reports/handoff.en.md` is the canonical handoff record for its `run_id`
- `state/handoff.en.md` is the latest control-shell mirror and must reference the archived per-run handoff path
- `artifacts/final/final-summary.en.md` is generated by the control shell during archive finalization
- takeover packets and takeover result records must stay under the triggering `run_id`
- reports are English repository-facing outputs
- approval summaries may remain Chinese because they are control-plane artifacts
- logs must be redacted before long-term archival
- evidence must remain stable enough for later review
- metadata must describe environment and timing context

## Retention Guidance

- keep contract, manifest, report, and checksum files for the full audit retention window
- keep approval card snapshots and decision receipts for the same retention window as freezes and change requests
- keep session exports when they materially support debugging or compliance
- allow lower-priority cleanup only for reproducible cache data

## Archive Readiness

A job is not archive-ready until:

- every executed `run_id` has `metadata/run-result.json`, `metadata/artifact-index.json`, and `reports/handoff.en.md`
- required role-specific reports exist
- approval card snapshots and decision receipts exist for all resolved approvals
- the manifest exists
- checksums have been generated
- `artifacts/final/final-summary.en.md` exists when the job reaches final archive state
- traceability can resolve each active story outcome
