# Official Reference Notes

## Purpose

This document collects official external references that support feasibility checks for CodingClaw.

Repository documents remain normative. External documents in this file are supporting evidence for technology choices, execution boundaries, and integration limits.

## Feasibility Verdict

- Phase 1 Docker workers are feasible.
- Bind mounts fit `repo`, `state`, and `artifacts` because both the host and the worker need direct file access.
- Docker volumes fit cache or container-owned persistent data better than additional bind mounts.
- SQLite is a reasonable Phase 1 metadata store only for single-node, local metadata with low write concurrency.
- PostgreSQL is the correct upgrade path once the system needs multi-process coordination, multi-client access, or higher write concurrency.
- The supported Phase 1 GUI surface is a single Ubuntu host with a local graphical session.
- The system should not depend on a cloud desktop vendor or remote-assistance bridge for normal automation.
- The executor-agnostic adapter contract is feasible, but capability declarations must stay profile-specific rather than assume one universal tool surface.

## Docker Worker Runtime

- `DEPLOYMENT_PLAN.md`, `ARCHITECTURE_OVERVIEW.md`, `SECURITY_POLICY.md`: bind mounts are appropriate when the host and the container both need direct access to source trees, configs, or generated artifacts.
  References: [Bind mounts](https://docs.docker.com/engine/storage/bind-mounts/), [Running containers](https://docs.docker.com/engine/containers/run/)

- `SECURITY_POLICY.md`: bind mounts are writable by default, so immutable inputs should use `readonly` or `ro` where possible.
  Reference: [Bind mounts](https://docs.docker.com/engine/storage/bind-mounts/)

- `DEPLOYMENT_PLAN.md`: volumes are the preferred mechanism for persistent data generated by and used by containers, especially when host-side file inspection is not required.
  References: [Volumes](https://docs.docker.com/engine/storage/volumes/), [Storage drivers](https://docs.docker.com/engine/storage/drivers/)

- `ARCHITECTURE_OVERVIEW.md`, `STATE_STORE_SPEC.md`, `DEPLOYMENT_PLAN.md`: disposable workers plus externally mounted state and artifacts are consistent with Docker's ephemeral writable layer model.
  References: [Running containers](https://docs.docker.com/engine/containers/run/), [Storage](https://docs.docker.com/engine/storage/)

## Metadata Storage

- `DEPLOYMENT_PLAN.md`: SQLite is appropriate for local application storage and is not positioned as a shared enterprise repository.
  Reference: [Appropriate Uses For SQLite](https://www.sqlite.org/whentouse.html)

- `DEPLOYMENT_PLAN.md`: SQLite should not be the long-term choice when many concurrent writers or many networked clients need the same database.
  Reference: [Appropriate Uses For SQLite](https://www.sqlite.org/whentouse.html)

- `DEPLOYMENT_PLAN.md`: PostgreSQL uses a client/server model and supports multiple concurrent clients.
  Reference: [Architectural Fundamentals](https://www.postgresql.org/docs/current/tutorial-arch.html)

- `DEPLOYMENT_PLAN.md`: PostgreSQL MVCC and advisory locks make it a better fit for scheduler coordination, queue ownership, and other multi-process control-plane workflows.
  References: [MVCC Introduction](https://www.postgresql.org/docs/current/mvcc-intro.html), [Explicit Locking](https://www.postgresql.org/docs/current/explicit-locking.html)

## Local Ubuntu GUI Runtime Baseline

- `UBUNTU_GUI_RUNTIME_PLAN.md`, `GUI_EXCEPTION_POLICY.md`, `DEPLOYMENT_PLAN.md`: the repository design keeps the control shell, workers, artifacts, and headed GUI surface on one Ubuntu host so audit paths and evidence paths stay local and deterministic.

- `TAKEOVER_FLOW.md`: human takeover remains a fallback path for blocked interactive steps. It is not the normal execution surface and does not require a cloud desktop vendor to exist.

## Executor And Adapter Boundary

- `EXECUTOR_ADAPTER_CONTRACT.md`: OpenAI Shell supports both hosted containers and local runtimes, which aligns with a generic adapter contract that separates capability declaration from the calling workflow.
  Reference: [Shell](https://developers.openai.com/api/docs/guides/tools-shell)

- `EXECUTOR_ADAPTER_CONTRACT.md`: approval hooks are supported at the tool layer, but the exact approval object shape remains a CodingClaw contract rather than an OpenAI-defined standard.
  References: [Shell](https://developers.openai.com/api/docs/guides/tools-shell), [Responses API reference](https://platform.openai.com/docs/api-reference/responses/retrieve)

- `EXECUTOR_ADAPTER_CONTRACT.md`: tool outputs can carry command results and artifacts, but repository archive structures such as `artifact-index.json` and `handoff.en.md` are still project-defined audit objects.
  References: [Shell](https://developers.openai.com/api/docs/guides/tools-shell), [Responses API reference](https://platform.openai.com/docs/api-reference/responses/retrieve)

## Limits Of External Proof

- No official Docker, SQLite, PostgreSQL, Alibaba Cloud, or OpenAI document defines CodingClaw's freeze contract, approval card schema, artifact archive structure, or trace index schema.
- No official external document in this review defines the full `takeover packet -> resume semantics` workflow or the exact local GUI orchestration rules used by this repository.
- These governance and audit objects remain internal platform design decisions. They are feasible, but their correctness must be validated by implementation and integration tests, not by vendor documentation alone.
